# Production Deployment — Render

Render was chosen for the free tier, automatic HTTPS, managed Postgres and health-check-gated
zero-downtime deploys. Images are built once in CI, pushed to GHCR and Render pulls the exact
`sha-<commit>` tag.

## One-time setup

### 1. Push the repo to GitHub

```bash
git remote add origin https://github.com/<you>/RBT-month5.git
git push -u origin main
```

The first run on `main` publishes `ghcr.io/<you>/blogflow-api` and `ghcr.io/<you>/blogflow-web`
(the deploy job fails until steps 3–4 are done — that's expected).

### 2. Make the GHCR packages public

GitHub → your profile → **Packages** → `blogflow-api` → Package settings → Change visibility →
Public. Repeat for `blogflow-web`.
(Alternatively keep them private and add a GHCR registry credential in Render — a PAT with
`read:packages` — then uncomment `creds` in `render.yaml`.)

### 3. Create the Render services from the Blueprint

1. Check the image owner in `render.yaml` (`ghcr.io/lakshitha-dev/...`) matches the GitHub account you pushed to.
2. Render dashboard → **New → Blueprint** → select the repo → **Apply**.
   This creates `blogflow-db` (Postgres 16), `blogflow-api` and `blogflow-web`.
3. Note the actual hostnames Render assigned. If they differ from
   `blogflow-api.onrender.com` / `blogflow-web.onrender.com`, update:
   - `blogflow-web` → env `API_UPSTREAM`
   - `blogflow-api` → env `CORS_ORIGIN`

### 4. Wire CI to Render

- Each service → Settings → **Deploy Hook** → copy into GitHub secrets
  `RENDER_BACKEND_DEPLOY_HOOK` / `RENDER_FRONTEND_DEPLOY_HOOK`.
- GitHub repository variables `API_URL` and `FRONTEND_URL` (the HTTPS URLs).
- Each service → Settings → **Auto-Deploy: No** (CI decides when to deploy).

### 5. Seed demo data (optional)

Render → `blogflow-api` → **Shell** (paid plans) or locally against the DB's *external* URL:

```bash
cd backend
DATABASE_URL="<external connection string>" DB_SSL=true node database/seeds/seed.js
```

## Deployment checklist (from the brief)

| Item | How it's done |
|------|---------------|
| Configure environment variables | `render.yaml` `envVars`; secrets generated by Render (`JWT_SECRET`, `METRICS_TOKEN`) |
| Set up database connection | `DATABASE_URL` from `blogflow-db` (internal URL); migrations run on boot |
| Configure custom domain | Optional: service → Settings → Custom Domains → add CNAME to `<service>.onrender.com`; then update `CORS_ORIGIN` / `FRONTEND_URL` |
| Enable HTTPS/SSL | Automatic — Render issues and renews Let's Encrypt certs for `*.onrender.com` and custom domains; HTTP redirects to HTTPS |
| Set up health checks | `/health/ready` (API, checks DB) and `/healthz` (web) |
| Configure auto-restart | Render restarts crashed containers and instances that fail health checks |

## Zero-downtime / blue-green

On each deploy Render starts the new container alongside the old one, waits for the health
check to pass, then switches traffic and stops the old one — a managed blue-green cutover.
If the new version never becomes healthy the deploy fails and the old version keeps serving.
CI additionally waits for `/health` to report the new `sha-…` before deploying the frontend.

## Free-tier caveats

- Free web services **spin down after ~15 min idle**; the first request afterwards takes ~1 min
  (CI's smoke test retries for this).
- Free Postgres **expires 30 days** after creation — upgrade or recreate before then.
- No pre-deploy command / shell on free instances — hence migrations run at container start
  (guarded by a Postgres advisory lock).
